# NR network profile and swin speed-up at 960x540, RX 6900 XT (2026-10-15, branch perf-fuse)

Base: origin/nr-split (native c32 from c32-fix). Data: `E:\dlss-runtime\c32fix\nr_data`. Delivery: `E:\dlss-runtime\perf_fuse` (`build\`, `nr_data\` = new, `nr_data_base\` = old, `src\` = scripts).
Timing: `runtime/nr_bench.cpp` (nr_run2 GPU time e0..e1 of the whole network, history on, median over 57 frames). The GPU is shared with other agents, so expect ±0.3 ms between identical runs.

## Tools
- **RGP / Radeon Developer Panel: not installed** (nothing under Program Files or E:). Only ROCm 6.4 is there, which has no rocprof on Windows. Nothing was installed.
- Instead: NR_PROF (an event after every dispatch), nr_bench, knockout builds (`src/mkko.py`, `KO` bitmask), and a hipGraph replay test.

## Launch gaps
- Whole frame without per-dispatch events: 23.94 ms. With 156 events: 24.57 ms. So one extra queue command costs about 4 µs.
- The tiny k_repack dispatches measure about 1 µs in NR_PROF, so back-to-back dispatch overhead is about 1-3 µs. Over 156 dispatches that is at most about 0.3-0.5 ms.
- **hipGraph replay of the full frame: 23.98-24.00 ms against 24.08 ms for stream launches**, which is within noise. The CPU runs far ahead of the 24 ms GPU frame, so the queue never drains. The graph code was not kept.
- Conclusion: the frame is not launch-bound. Merging elementwise kernels would gain nothing either: the only tiny dispatches are import, export and repack (<0.2 ms together).

The swin blocks are **already one fused kernel per block**: qkv, attention, proj and MLP for one 8x8 window run in a single workgroup, all in LDS. So step 3 ("fuse the swin chain") was already done in an earlier round. The remaining question is what inside the kernel costs time.

### Swin c64+c128+c256 stage shares (knockout: time saved when a stage is removed, of 11.25 ms)

The removals overlap, so the shares do not add up. The GEMM loops are dot2-issue-bound (see RESULTS_swin_big on perf-swin2: 512-thread and 8x8-tile variants were slower). The cheapest non-dot lever was the weight staging.

## Change kept: W16, an f16 weight shadow (bit-exact)
- `native/swin_var.hip` (perf-swin2 source, `W16=1`): every weight piece a workgroup stages is read from an f16 copy of the record, at 2x the record offset. The copy is already in LDS row order, so a staging thread does 2 global dwordx4 loads and 2 `ds_write_b128`. Before, it did 1 load, 8 e4x2 unpacks and 8 scattered `ds_write_b32`. VGPRs are unchanged (≤254) and nothing spills.
- New kernels `k_swin_c{64,128,256}[s]_prep` build the copy once per record at load into a 64 MB module pool (about 40 MB used at 540p).
- Runtime (`nr_create`): if an override module exports `<sym>_prep`, it runs once per weight record, and the shadow pointer goes to kernarg +0xa0 (unused padding of VarParams). Old modules have no `_prep` and behave as before.
- **Quality:** the shipped-config flicker harness (history=1, vit_every=2, reuse=bottleneck, 60 frames) produced **all 120 dumped frames byte-identical** to the base at 540p and at 720p. Flicker is unchanged: x1.11 / network x1.39 at 540p, x1.08 / x1.34 at 720p. The nr_bench output is byte-identical too.
- Tried and dropped: the same change in k_swin_c32. It was bit-exact, but saved only ~0.03 ms and added an 8 B scratch spill.
