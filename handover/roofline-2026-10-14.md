# Roofline analysis of the 960x540 DLSS-NR network on the RX 6900 XT (2026-10-14, B0 + B2)

Inputs: `ops-count-2026-10-13` (MACs per layer), `E:\dlss-runtime\skip\nr_data\960x540` (manifest, overrides, meta), the native sources (native-c512, native-mid, native-prepost, `handover/game-ready-sync/native` on perf-vit2/perf-b2), and three NR_PROF runs of v0.2.3 on the harness (`E:\dlss-runtime\b2`).

## Machine assumptions
- **dot2 peak:** 80 CU x 64 lanes x 2 MAC at 2.25 GHz = 23.0 TMAC/s (20.6 at the 2.015 GHz game clock). The percentages below use 23.0.
- **DRAM:** 512 GB/s. The ridge point is 45 MAC/B.
- **Infinity Cache:** 128 MB at an assumed ~1.8 TB/s effective, so its ridge is ~13 MAC/B. Most of the per-frame working set (activations ≤ 42 MB per buffer, ViT weights 96 MB) is IC- or L2-resident between neighbouring dispatches.
- **LDS:** assumed 128 B/clk per CU in CU mode (`-mcumode`), against 128 MAC/clk per CU of dot2. So a kernel that reads **1 B of LDS per MAC** is LDS-bound at the same rate as it is dot2-bound. With imperfect overlap that lands near 50 % of peak.
- Bytes are fp8 (e4m3) activations and weights at 1 B each, counted once per dispatch: weights + input + output (+ skip/residual). Re-reads inside a kernel (weights once per token block) are noted separately; they hit L2/IC.

## Correction to the family mapping in ops-count-2026-10-13
That table divided each kernel's time by MACs from an assumed family mapping. The dispatch list shows two mappings that are wrong:
- `k_conv2_n` (the "c512 conv" row) runs **both** SplitProj **and** SplitFfwdProj: 31 dispatches x 167.8 MMAC = 5.2 GMAC, not 2.52. `k_ffwd2_n` runs **only** SplitFfwd: 16 x 335.5 MMAC = 5.37 GMAC, not 8.05.
- `k_vit_contract_n` runs **both** VitFfnContract (K=4096) **and** VitProjection (K=1024): 16 dispatches, 8.05 GMAC, not 6.44. `k_attention2` is VitAttention only (0.60 GMAC).

Corrected, using the median NR_PROF of v0.2.3 runs base1/base2 (one frame each; run base0 had an 11 ms one-off stall in one contract dispatch, which is excluded):

| kernel (family) | dispatches | GMAC | ms | TMAC/s | % peak | per dispatch |
|---|---:|---:|---:|---:|---:|---|
| k_conv2_n (c512 Proj + FfwdProj) | 31 | 5.20 | 0.53 | 9.8 | **43 %** | 18 µs, grid 10x8 = 80 WG, K=512 (8 chunks) |
| k_ffwd2_n (c512 Ffwd) | 16 | 5.37 | 1.09 | 4.9 | **21 %** | 63 µs, grid 10x8 = 80 WG |
| k_qkv_attn_n (c512 attention) | 16 | 11.78 | 1.60 | 7.4 | 32 % | 100 µs |
| k_vit_expand_n | 8 | 6.44 | 0.79 | 8.2 | 36 % | 95 µs, 3x64 = 192 WG, K=1024 |
| k_vit_qkv_n | 8 | 4.83 | 0.49 | 9.9 | 43 % | 61 µs, 3x48 = 144 WG |
| k_vit_contract_n K=4096 | 8 | 6.44 | 1.05 | 6.1 | **27 %** | 131 µs, 3x16 = **48 WG**, 64 chunks |
| k_vit_contract_n K=1024 | 8 | 1.61 | 0.32 | 5.0 | **22 %** | 40 µs, 48 WG, 16 chunks |

So **"c512 conv at 20 %" does not exist**: `k_conv2_n` is the most efficient C=512 kernel (43 %). The C=512 kernel at half its siblings' rate is `k_ffwd2_n` (21 %). The ViT contract gap is real (27 % / 22 % against 36-43 %).

**Every family is far to the right of both ridges** (45 MAC/B for DRAM, ~13 for IC). Even if every byte came from DRAM, the whole frame needs only ~0.9 ms of DRAM time against ~26 ms measured. **None of the network is memory-bound.** The limits are inside the CU:

1. **LDS bandwidth in the GEMM kernels** (`gemm64`: ViT expand/qkv/contract, conv2, and the qkv GEMM in qkv_attn). The inner kd loop is clean: 98 % of its VALU is v_dot2. But it reads 16 `ds_read_b128` per 128 dot2 per lane, i.e. a 4x4 register tile = **1.0 B of LDS per MAC**, which matches the assumed 128 B/clk against 128 MAC/clk. These kernels top out at 36-43 %, consistent with an LDS-bound GEMM whose dot2 and LDS issue do not fully overlap.
2. **Non-dot VALU in the Swin, pre and post kernels.** The fp8→f16 unpack (`e4x2`: and/shift/or), the f32→f16→e4m3 requantisation (`q8`/`to_e4m3`: min/abs/add/and/cndmask), softmax, LayerNorm-like scaling and address math. Static ISA counts per loop level (`imix.py` on the gfx1030 .s; dynamic weights not measured):

| kernel | innermost loop: dot2 / other VALU / ds | next level (per chunk/window step): dot2 / other VALU | straight-line (epilogue, softmax, requant): dot2 / other VALU |
|---|---|---|---|
| gemm64 kernels (conv2, ViT, qkv) | 128 / 2 / 16 | 0 / 154 (144 bitops: fp8 unpack + LDS addressing) | 0 / 520-1200 |
| → per 64-k chunk | 512 dot2 : ~160 other VALU = **76 % dot2** | | |
| k_ffwd2_n | 384 / 6 / 48 | 0 / 681 (276 float, 344 bitops) | 0 / 1076 |
| k_qkv_attn_n | 256 / 4 / 32 | 16 / 371 | 256 / 1215 |
| k_swin_c256 | 224 / 4 / 22 | 832 / 633, then 256 / 3034 | 1056 / **8219** |
| k_swin_c128 | 224 / 4 / 22 | 480 / 480, then 256 / 2124 | 704 / **6631** |
| k_swin_c64 | 32 / 2 / 5 | 112 / 73, 152 / 683, 256 / 1560 | 296 / **4811** |
| k_swin_c32 (native, opt-in) | 128 / 4 / 30 | 224 / 432 | 480 / 4190 |
| k_pre_native | 512 / 700 (no LDS; 43 vmem, 1919 SALU) | | 8576 / **14149** |

In the Swin kernels most of the VALU outside the innermost GEMM loop is non-dot work. Of that, fp8 conversion (cvt + bitops) is about 40-50 % and float/compare (softmax, requantisation, cndmask) is 50-60 %. This matches the earlier profiling finding that non-dot VALU dominates. The kernels are **VALU-issue-bound on overhead**, not on MACs.

### Bytes, rule of thumb
At 540p each activation tensor is ≤ 4.4 MB (C=32) and drops 2x per stage. Weights total ~100 MB per frame (ViT 96 MB, all Swin < 25 MB). Cutting bytes (fp8 everywhere already, fused blocks) will not move the frame time. Cutting **instructions per MAC** will.

## Ranked: where effort pays off (540p, ~26 ms)

1. **Swin c64/c128/c256 + pre + post, non-dot VALU (~14.6 ms, 24-28 %).** This is the biggest lever. Unpack fp8 to f16 once, when staging into LDS, instead of per use. Requantise only at block outputs. Vectorise softmax with packed f16 (`v_pk_*`). Move pre's SALU-heavy loop (1919 SALU per iteration) to VALU or tables. Reaching 40 % saves ~5 ms.
2. **swin c32 (5.0 ms, 16 %).** The native exact path (B1, `swin_c32.hip`) is the obvious route: −1.6 ms measured for the lossy version, more if its hazard is fixed and the same overhead cuts as in item 1 apply.
3. **gemm64 register tile 4x4 → 8x4 (LDS 1.0 → 0.75 B/MAC) or 8x8 (0.5 B/MAC).** Affects ViT expand/qkv/contract, conv2 and the qkv part of qkv_attn: ~4.8 ms at 32-43 %. +20-30 % on these is ~1 ms. It is bit-exact (each output keeps its dot2 order), but needs ≤128 VGPR (8x8 = 64 acc + 16 operands fits). Note that fewer outputs per thread (the opposite direction) was measured slower, see B2.
4. **k_ffwd2_n (1.09 ms, 21 %).** It runs 80 WGs = one per CU through three dependent GEMMs. perf-c512b's 20 KB-LDS version (3 WG/CU) was run here for the first time. It is **byte-identical** (3/3 runs), but the NR_PROF single-frame timing could not separate it from noise (1.09 → 0.96/1.04/1.13 ms), so it is not merged. It needs a longer timing method, e.g. NR_PROF over many frames. Potential ~0.4 ms at 40 %.
5. **ViT contract (done, B2): −0.11 ms.** See below. The remainder (K=1024 projection at 22 %, 48 WGs) is worth < 0.15 ms.
6. Not worth it: conv2 (already 43 %), attention2 (0.3 ms), import/export/final_head/upsample/conv_res_views (< 0.5 ms together).
7. **B5 (int dot4)** only pays if items 1 and 3 are done first. The GEMM loops are LDS-bound and the Swin kernels VALU-overhead-bound, so a 2x faster MAC instruction alone changes little.

## B2: ViT contract and "c512 conv"

**c512 conv:** there is no 20 % kernel. The family mapping counted only SplitProj for `k_conv2_n`, which also runs every SplitFfwdProj (31 dispatches). Its real rate is 43 % of peak, so nothing was changed. The C=512 kernel that really runs at half rate is `k_ffwd2_n` (item 4).

**ViT contract, root cause:** the launch shape. Expand, qkv and contract use the same `gemm64` (64 tokens x 64 outputs per 256-thread WG, 4x4 per thread, same swizzled LDS, same VGPR/LDS = 106-108 VGPR, 32 KB). The 192 tokens give 3 token blocks, so:
- expand: 3 x 64 = 192 WGs, K=1024 (16 chunks): 2 WGs per CU on all 80 CUs;
- contract: 3 x 16 = **48 WGs**, K=4096 (**64 chunks**): one WG per CU on 48 CUs, 32 CUs idle, each a 4x longer serial chain at 4 waves per SIMD.

Per-CU throughput is about the same in both (≈0.5 chunk/µs/CU). The contract simply uses 60 % of the GPU.

Tried (all on the harness, NR_PROF, outputs compared with v0.2.3):

| variant | WGs | K=4096 dispatch | result |
|---|---:|---:|---|
| v0.2.3 | 48 | 0.131 ms | - |
| 32 tokens per WG (2x4 per thread), bit-exact | 96 | 0.170 ms | slower: 2x the weight re-reads, 96 WGs on 80 CUs is uneven |
| 16 tokens per WG (1x4 per thread), bit-exact | 192 | 0.216 ms | slower: 4x the weight re-reads, LDS bytes per MAC up |
| **two K-halves per 512-thread WG** (kept) | 48 | **0.118 ms** | f32 lo+hi reassociation; deterministic |

**Fix (branch perf-b2, `handover/game-ready-sync/native/vit_swz.hip`):** `k_vit_contract_n` now launches 512 threads. Group h = tid>>8 runs K half h (chunks h·NC/2 .. (h+1)·NC/2) on its own 32 KB of LDS (64 KB per WG). Group 1 passes its 16 f32 sums per thread to group 0 through LDS, and group 0 adds them (`__fadd_rn(lo, hi)`) and runs the unchanged epilogue. Override line (`overrides_vit_ks.txt`):
`_Z11k_contract212ConvParams1d|kernels\native_vit.co|k_vit_contract_n|=|16|=|512|424|0<-0:424`
With the old 256-thread line the same .co runs all of K in one group and is byte-identical to v0.2.3 (checked).

**Timing (NR_PROF, frame 5, 960x540, history=1, vit_every=1):**
- k_vit_contract_n: v0.2.3 1.362 / 1.399 ms (third run 12.3 ms one-off stall) → new 1.272 / 1.320 / 1.249 ms (final build 1.214). That is **−0.11 ms (−8 %)**: per dispatch 0.131 → 0.118 ms (K=4096) and 0.040 → 0.035 ms (K=1024).
- Network TOTAL (single-frame prof; ±0.4 ms noise): 26.15 / 26.26 → 25.70 / 25.61 / 25.87 / 25.63 ms.
- The end-to-end `test_sync` normal mode (200 frames nr_run, CPU in/out included) drifted ±1 ms between identical runs on the shared GPU. It cannot resolve a 0.1 ms change and is not used.

**Quality:** the harness dumps (60 frames network-alone, f32 RGB) are **byte-identical to v0.2.3 in 7 of 8 runs** of the new kernel. The f32 reassociation only rarely changes an f16→e4m3 rounding. One run (ks1) had a single frame (f057) at **51.0 dB**, with the other 59 identical. A rerun of the same build was fully identical, so this is either a rare run-to-run effect or a single rounding flip. Mean PSNR is therefore ≥ 98 dB (identical frames counted as 99) and the worst is 51 dB, against the ≥ 40 / ≥ 35 dB thresholds. Flicker is unchanged: frame x1.11 (0.221 % white jumps), network-alone x1.41 (1.475 %), the same as v0.2.3.
